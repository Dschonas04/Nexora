# Templates for the home-server platforms

Nexora is three containers plus PostgreSQL, so most platforms take it as a
Compose stack rather than as a single image. What lies here is the stack in the
shape each store wants.

**None of these has been tested on a real installation of that platform yet**,
they follow the documented format, and the compose part underneath is the same
[`docker-compose.stack.yml`](../docker-compose.stack.yml) that has been. If one
of them does not take, an issue with the error is worth more than a polite
silence.

The templates pull from the GitHub Container Registry
(`ghcr.io/dschonas04/nexora-*`). The same images with the same tags are on
Docker Hub as `dschohnas/nexora-*`; replace the prefix to use those instead.
Both are built for amd64 and arm64.

Two values have to change before any of this runs anywhere real:
`POSTGRES_PASSWORD` and `JWT_SECRET`. The second signs the sessions; left at
the example, anybody who knows it can be anybody.

```bash
openssl rand -hex 32
```

## Portainer, Coolify, Dokploy, Komodo

No template needed. These take a Compose file as it is: create a stack, paste
[`docker-compose.stack.yml`](../docker-compose.stack.yml), set the two values,
deploy. The interface answers on port 3000 unless `PORT` says otherwise.

## Unraid

Two ways, depending on whether a PostgreSQL already runs on the server.

### Container templates, with your own PostgreSQL

[`unraid/`](unraid) holds one XML template per container:
`nexora-backend.xml` for the service and `nexora-frontend.xml` for the
interface. They leave the internal certificate authority out and talk plain
HTTP inside a Docker network of their own, which is why both have to sit in
the same one:

1. Create the network once, in the Unraid terminal:
   `docker network create nexora`.
2. Create a database and a user for Nexora in your PostgreSQL (16 or newer).
3. Copy both XML files to `/boot/config/plugins/dockerMan/templates-user/`,
   then *Docker → Add Container* and pick `nexora-backend`. Fill in the
   database URL and a JWT secret (`openssl rand -hex 32`), apply.
4. Add the second container from `nexora` the same way. The interface answers
   on port 3000; the first account that registers is the administrator.

The backend needs the network alias `backend`, which the template sets in
*Extra Parameters*; the interface looks for the service under that name.
These templates need images from 2.2.0 on: earlier frontends refuse to start
without the certificate authority.

### Compose Manager, with the bundled database

Unraid's Community Applications are built around one container per template,
so the whole stack goes through the **Compose Manager** plugin
(Apps → Compose Manager):

1. Add a new stack, name it `nexora`.
2. Paste [`docker-compose.stack.yml`](../docker-compose.stack.yml) as the
   compose file.
3. Put `POSTGRES_PASSWORD` and `JWT_SECRET` into the stack's `.env`, and
   `PORT` if 3000 is taken.
4. Compose Up.

The attachments live in the Docker volume `nexora_files` by default. To put
them on a share instead, replace that volume with a bind mount to
`/mnt/user/appdata/nexora/anhaenge`.

## CasaOS

[`casaos/docker-compose.yml`](casaos/docker-compose.yml) carries the CasaOS
metadata in the `x-casaos` block. Import it through *App Store → Custom Install
→ Import*, then change the two values in the environment section before the
first start.

## Umbrel

[`umbrel/`](umbrel) holds `umbrel-app.yml` and the compose file in the layout an
Umbrel app store expects: the directory is named after the app id
(`nexora`), and both files sit in it. For a private app store, drop the folder
into the store repository and point Umbrel at it.

`APP_PASSWORD` and `APP_SEED` are filled by Umbrel, so nothing has to be
generated by hand there.

## What is still missing

- A **TrueNAS SCALE** app, which would need its own chart.
- **Yunohost** and **Cloudron** packages, each with its own format.

Anybody who runs one of these platforms and wants to fix a template: the
compose file is the whole logic, the rest is metadata.
